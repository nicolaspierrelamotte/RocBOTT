- Tests : `tests/test_colibri_reproduction.py::test_detector_called_on_the_pipeline_flags_acausal_filter_and_clears_causal_one` (le filtre de Colibri est attrapé via le `Pipeline`, aucune `decide` écrite à la main : 21/100 et 34/150 décisions changées ; version causale 0) ; `::test_signal_that_reads_the_future_is_caught_through_the_pipeline_even_without_filter` (fuite portée par le signal) ; `::test_trade_level_detector_runs_the_executed_chain_and_agrees` ; `::test_pipeline_decide_is_what_simulate_trades_executes` ; `tests/test_lab_pieces.py` (contrat).
- Ancien code : `detect_leak(pipeline)` → `TypeError: 'Pipeline' object is not callable` ; une `decide = pipeline.signal` donne n_changed = 0 (c'est encore vrai, à dessein : un signal nu n'est pas la chaîne, d'où `Pipeline.decide`).
- Ce qui reste, NON résolu : seules les barres (`bars`) sont perturbées. Un pipeline qui lit une donnée hors de `bars` (tableau précalculé avec décalage vers l'avenir, autre instrument, paramètres estimés sur tout l'échantillon, HMM ajusté sur toute la série) n'est pas vu, et le module le dit dans sa docstring. Paramètres choisis sur l'historique complet (M3) : non rejoués. Rien dans `scripts/` n'appelle encore le détecteur : c'est hors de mes fichiers (`write_acausalite_json` est l'appel prévu).

### F-4 — Stop/objectif soldés au niveau, zéro du témoin faux — **résolue**
- Fait : stop soldé au pire du niveau et de l'ouverture de la barre (gap) + `stop_slippage_bp` explicite ; objectif au niveau, jamais mieux ; stop prioritaire conservé et documenté. `expected_r_from_spread = -péage/stop` supprimé : le R attendu est calculé par `expected_r_under_null` (mêmes instants de décision, sens tiré à pile ou face indépendant des prix, même mécanique et mêmes coûts). `ControlResult` expose `expected_r`, `expected_r_se`, `excess_r`, `t_excess`.
- Tests : `tests/test_lab_execution.py::test_stop_on_a_gap_fills_at_the_open_not_at_the_level` (+ court, objectif, stop prioritaire, glissement) ; `::test_asymmetric_stop_and_target_zero_drift_has_no_significant_excess[10-30, 30-10]` (stop ≠ objectif, dérive nulle : |t_excess| < 3 — valeurs 1,16 et 0,87 — alors que le t du R brut est 5,34 et −7,20 : le « zéro » naïf est faux et le test l'affirme) ; `::test_expected_r_with_spread_is_computed_not_assumed`.
- Ancien code (mesuré, graine 31, stop 10 / objectif 30) : R stop sur gap = −1 au lieu de −5 ; R brut +0,051 contre « attendu » 0, t = +5,25.
- Reste : sur la marche synthétique le chemin n'est connu qu'à 20 pas par barre ; le fill reste au niveau (pas de gap dans le synthétique), donc le biais de dépassement sur grille subsiste dans R mais il est ABSORBÉ par le R attendu, qui rejoue la même mécanique. Il n'est pas supprimé. Le niveau du biais dépend de `steps_per_bar = 20`. La référence à sens aléatoire est valide pour un pipeline sans compétence ; elle suppose que les instants de décision du signal ne dépendent pas du sens (ce que fait un suiveur de barre, pas tout signal). Faux positifs : sur 30 graines × 3 géométries, |t_excess| > 3 dans 3 cas sur 90 (attendu ~0,2) avec la référence à 3 × ; écart-type de t entre 1,1 et 1,3, moyenne négative de −0,3 non expliquée ; je n'ai pas re-mesuré avec la référence à 5 ×. Le seuil de 3 de la porte P3 n'est donc pas un seuil à 0,27 % de faux positifs : c'est plus.

### F-8 — « Seuil de détection » = un tirage unique — **résolue**

### F-11 — Avantage planté = saut à l'ouverture, hors position — **résolue pour le test de puissance**
- Fait : `online_planted_path` génère la marche barre par barre ; la dérive n'existe que pendant que la position est tenue, dans son sens, jamais hors position ni hors filtre ; avantage nominal = bp par trade en moyenne (dérive par barre = edge / durée moyenne tenue sous le nul) ; avantage réalisé mesuré sur les trades et rapporté à côté (`realised_edge_bp`). `plant_edge` est conservé comme outil bas niveau, documenté comme un saut, et n'est plus utilisé par le test de puissance.
- Tests : `tests/test_power.py::test_edge_is_planted_only_while_in_position_and_in_its_direction`, `::test_online_generation_without_edge_is_the_walk_and_the_simulation` (sans avantage, la génération en ligne égale la marche et `simulate_trades` trade par trade), `::test_bar_from_steps_matches_random_walk_bars_with_drift`, et l'assertion `realised ≈ nominal à 10 %` du test de probabilité.
- Reste : valable pour un signal et un filtre CAUSAUX (le signal est évalué sur un préfixe) : un pipeline acausal n'a pas de sens ici. L'avantage est une dérive uniforme dans la barre ; un avantage dépendant de l'ordre intra-barre ou d'une latence n'est pas représenté. Le signal est recalculé sur les barres déformées, donc l'avantage réalisé peut différer du nominal : il est mesuré (7,7 pour 8 ; 3,97 pour 4).

### F-12 — `ftmo.py` : clôture au lieu de l'équité intra-journalière — **résolue pour la perte journalière et la perte maximale ; frontière de journée non traitée**
- Fait : `barrier_probability(..., daily_low=...)` accepte le plus bas intra-journalier de chaque jour (depuis l'ouverture du jour, fraction du capital initial), rééchantillonné avec la clôture ; il est testé avant la clôture du jour : perte journalière puis perte maximale statique (équité d'ouverture + creux). Le résultat porte `equity_basis` : `"intraday"` ou `"close_only"` ; sans `daily_low` la docstring dit que la probabilité est un majorant. Validation : un creux au-dessus de la clôture ou de mauvaise longueur lève `ValueError`. Le produit p1 × p2 supposé indépendant est dit dans la docstring de `two_step_pass_probability`.
- Tests : `tests/test_ftmo.py::test_a_day_closing_at_minus_3_but_touching_minus_6_fails_the_5_percent_rule` (p_daily_loss 1,0 avec creux, 0 sur clôtures seules et le résultat dit `close_only`), `::test_intraday_low_breaches_the_static_max_loss_even_if_the_close_recovers`, `::test_daily_low_is_resampled_jointly_with_the_close`, `::test_daily_low_validation`.
- Ancien code : `barrier_probability() got an unexpected keyword argument 'daily_low'` ; sur clôtures seules p_daily_loss = 0,0 sans aucun avertissement.
- Reste : la frontière de journée (fuseau, heure de roll) est celle de l'appelant, ni vérifiée ni modifiable ici ; l'appelant doit calculer le creux intra-journalier sur l'équité flottante (cela dépend du pipeline). Le test de la perte maximale ne couvre qu'un cas court. E-002 (le coupe-circuit du modèle de compte lisant la clôture) concerne le modèle de compte, pas `ftmo.py` seul : « à écrire » reste vrai pour ce modèle.
